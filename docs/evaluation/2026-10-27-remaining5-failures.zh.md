## 已确认的原因

最终错误分为 3 个修正请求超时、2 个重复无效配额结果。5 个实体均在 Stage 2
失败，未进入 Stage 3 或 Stage 4。实体间依次处理，Stage 4 候选并发没有与这些
Stage 2 请求重叠，因此不能把本轮超时归因为 Stage 4 并发。

新 Schema 和反馈改善了事实证据引用及理由字段：这 5 个实体已记录的各轮错误
中，没有跨事实证据引用和空理由错误。仍然失败的业务约束是候选总数、支持角色
以及 `insufficient_evidence` 的全局一致性。

配额错误存在明显模式：模型给每个保留的事实分配一个候选，但“每个事实都要出现”
不等于“每个事实都要生成候选”。`secondary` 可以保留且配额为 0；6 或 7 个事实
仍应共享 5 个候选预算。普通字段类型、枚举和数组长度约束不能检查多个
`candidate_quota` 的算术和，这一规则仍依靠本地校验与模型修正。

超时只证明客户端在等待修正响应时触发超时。现有记录没有 HTTP 429 或服务端
排队指标，不能确定是代理排队、服务端处理缓慢还是网络问题。重复 JSON 也不能
单独证明中转接口缓存了响应或忽略了提示词。

## 后续改进建议

1. 配额结构可采用由模型填写的固定 5 个候选锚点，再由程序计数得到各事实配额。
   模型仍拥有分配决策；程序不私自删除引用、修改角色或补齐配额。
2. 在 `insufficient_evidence` 状态下，通过对应 Schema 分支将角色限制为
   `context` / `excluded`、配额限制为 0，提前限制状态与字段之间的矛盾。
3. 将网络重试与业务修正次数分别限制。对修正请求超时提供有限重试和总时间上限，
   记录每次请求的耗时及错误；不靠无限增加修正次数掩盖原始配额问题。
4. 修复后优先只重跑这 5 个实体的 Stage 2，检查业务结果，再决定是否生成图片。
