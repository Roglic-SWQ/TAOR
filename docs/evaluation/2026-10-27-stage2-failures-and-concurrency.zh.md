## 共同原因与修正机制的局限

1. 当前响应 Schema 约束了字段类型和事实 ID，但 `evidence_refs` 只限制为字符串，
   没有把每个事实的合法引用集合绑定到其对应的输出项。`reason` 也允许空字符串。
2. 候选配额总和、辅助事实最终角色属于跨条目的业务规则，普通字段类型约束无法保证。
3. 现有修正只有一次，反馈通常只包含首个错误的笼统描述，缺少具体事实 ID、非法引用、
   合法引用集合以及其余同时存在的错误。
4. 16 个失败响应都经过一次修正，其中 13 个修正前后 JSON 的语义完全相同。
   这说明本批次的修正效果有限，不能据此断言上游缓存、模型替换或中转丢弃参数。

后续应优先收紧 Stage 2 的逐事实 Schema，明确区分当前事实引用和辅助事实引用，
约束非空理由，并把所有具体校验错误作为明确的修正指令反馈给模型。若再次更改配额
输出结构，应确保配额仍来自模型的显式规划，而不是程序偷偷改写角色或补足数量。
本次只分析这些失败，没有关闭校验或自动修补历史计划。

## 已实现的并发

Stage 4 的独立候选评分使用可配置的有限并发。主配置、GPU 可见设备配置和配置示例
已设置 `gpt4omini_judge.max_concurrency: 3`。该字段省略时默认 1，支持继续按串行运行。

- 同一实体最多同时发出 3 个评分请求；5 个候选不再逐个等待。
- 结果和调用日志按照输入候选顺序合并，评分、排序和拒绝规则保持原定义。
- 单个请求的服务异常或 JSON 异常仍归属对应候选，不会错配到其他图像。
- 本地 CLIP、BLIP、Sentence-BERT、BERTScore 等调用在主线程执行。
- worker 中的 HTTP 使用异步取消保持总请求超时；不在线程中调用 SIGALRM。
- 超时、429 和临时服务错误有界重试，数值型 Retry-After 最长等待 60 秒。
- 调用日志记录包括重试在内的真实墙钟耗时，后续可据此分析瓶颈。

当前安装或重建运行环境统一使用 `requirements.txt`，其中包含并发请求所需的 `httpx`。
Stage 0/1/2 之间有数据依赖，继续顺序执行。Stage 3 提示词生成未在本次改动中并发。
